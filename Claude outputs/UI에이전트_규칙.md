## ⚠ 「코드는 안 만진다」가 충돌을 없애지는 않습니다

파이썬을 안 만져도 **이 파일들은 여전히 공유**입니다:

    sourcing_guard/static/index.html   ← P4 가 showcase 구역을 여기 넣습니다
    sourcing_guard/static/app.css      ← P4 가 카드 스타일을 여기 넣습니다
    나머지 화면 7장

그리고 **검사가 이 파일들을 읽습니다** — `test_frontend.py` 의 `PAGES`,
`srccheck.markup_only`, 이모지·단정 표현 가드. 즉 **UI 작업도 검사 숫자를
흔듭니다.** 오늘 검사 결과가 회차마다 달랐던 원인이 그것입니다.

## 순서 — 이대로만

    ① **P4 를 먼저 올립니다.** UI 는 그동안 `index.html`·`app.css` 를
       건드리지 않습니다
    ② P4 배포와 확인이 끝나면 알려 드립니다
    ③ 그 뒤에 UI 작업을 시작합니다

**①이 끝나기 전에 그 두 파일을 열지 마십시오.** 반쯤 써진 파일을 서로
읽으면 검사 결과를 아무도 못 믿게 됩니다.

## 배포 — 기본은 **커밋만**

    UI 작업은 커밋까지만 합니다. 배포는 총괄이 판단합니다
    ⚠ 「고치는 것」 중 투표자에게 실제로 보이는 결함(예: 특정 폭에서 글자가
      잘린다)이 나오면 **먼저 알려 주십시오.** 그건 배포를 열 수 있습니다

## 작업할 때

    커밋 전에 `git status` 를 보고 **남의 변경이 섞였는지 확인**합니다.
      섞였으면 커밋하지 말고 알립니다
    `git add -A` 를 쓰지 않습니다. **명시 경로로만** add 합니다
      (오늘 이 저장소에서 두 번 났습니다)
    배포했다면 **바뀐 것을 열어서** 확인합니다. `fly deploy` 성공도
      `/healthz` 의 빌드 해시도 배포된 것이 아닙니다 — 해시는 build-arg 라
      트리와 어긋날 수 있고, **오늘 실제로 어긋났습니다**

## 화면을 고칠 때 이 저장소의 규칙 넷

    ① **폭을 재는 캡처가 아니면 못 잡습니다.** 1440 / 1280 / 1024 / 768 /
       390 / 320 · 다크 — 폭마다 `scrollWidth > innerWidth` 를 단정합니다
    ② **캡처는 장수가 아니라 높이를 셉니다.** 같은 수가 반복되면 `full_page`
       가 안 걸린 신호입니다 (전에 21장 중 14장이 뷰포트 조각이었습니다)
    ③ **틀이 아니라 틀에 붓는 값을 봅니다.** 화면 문구는 대개 자료에서
       옵니다 — `data/*.json` 도 같이 봐야 합니다
    ④ **새 격자의 `minmax(N,1fr)` 하한이 곧 최소 폭입니다.** `min(N,100%)`
       로 감쌉니다. 1280 에서는 멀쩡하고 320 에서만 넘칩니다
