시피님 판단이다. 내 본선 목록이 **진짜 막힌 것**인지 **안 재 보고 미룬 것**인지

## 0. 내가 틀렸던 것 둘

### (1) 상품 정보 표 — "추출 필드가 없다" ← **틀렸다. 정부가 준다**

`kats_client.py:466 CertRecord` 를 열어 보니 이미 들고 있다.

```
brand_name      ← 시안의 "브랜드/제조사"
model_name      ← 시안의 "모델명"
maker           ← 제조사
maker_country   ← 시안의 "제조국"
category_name · importer · cert_date · detail_url
```

**시안의 상품 정보 4칸이 전부 국가기술표준원 조회 응답에 있다.**
추출 프롬프트를 건드릴 이유가 **하나도 없다.**

⚠ 오히려 이쪽이 낫다 — LLM 이 읽은 값이 아니라 **정부 DB 등록값**이다.
  근거 링크(`detail_url`)도 따라온다 (R2). 조회 실패면 이 칸이 **안 뜬다**,
  그게 정직한 동작이다.

지금 `kc_verified` 가 `product_name` 만 쓰고 나머지를 버린다.
**버리지 말고 `detail` 에 실어 화면까지 보내면 끝이다.** 배관 작업이다.

### (2) 물놀이 매처 — "235 재측정을 부른다" ← **틀렸다. LLM 0회다**

`scripts/replay_single_path.py` 머리 주석:

> 저장된 LLM 답으로 단건 경로를 재생한다. **LLM·네트워크 0회.**
> 추출 결과가 바뀌지 않는 변경(**별칭·가드·표**)에서는 저장된 `facts` 를
> 그대로 되돌려 `verify()` 만 다시 돌리면 같은 숫자가 나온다.

별칭·제외표지 수정이 **정확히 그 부류다.** 235행 fixture 가 이미 있다.
내가 **추출 변경(LLM 235회)** 과 **매처 변경(0회)** 을 섞어서 말했다.

## 1. ⚠⚠ 그런데 순서가 하나 걸린다 — **제출 전에 결론 나야 한다**

물놀이를 고치면 **다섯 숫자가 움직일 수 있다.** 그 숫자는 랜딩·README·기획서·
제출문·「우리가 틀린 것」에 전부 적혀 있다.

    시피님이 104 / 77.0% 로 제출한 뒤에 숫자가 바뀌면
    → **제출 서류와 살아 있는 사이트가 서로 다른 말을 한다**

그래서 **이것부터, 그리고 제출 전에** 한다. 재생은 공짜니 먼저 재고 정한다.

```
1. 별칭 고침 없이 재생 → 지금 값 확인 (104 · 0 · 104 · 0 · 3)
2. 고침 넣고 재생 → 다섯 숫자와 **바뀐 행 수**
3. 바뀐 행이 적으면(한 자릿수) 손으로 검수하고 `[기준선 변경]`
   많으면 **되돌리고 그대로 간다** — 검수 못 한 줄이 들어가면 ② 가 0 이 아니게 된다
4. 어느 쪽이든 결론을 시피님께 먼저 알린다. 제출은 그 다음
```

⚠ 고침 방향: 「물놀이」는 상황어이므로 **핵심명사에 걸릴 때만** 쓴다. 같은
  파일에 `_ITEM_EXCLUSION_MARKERS` 와 부속품명 장치가 이미 있다 —
  새 기계를 만들지 말고 그것들을 쓴다.
⚠ 숫자가 **내려가도 넣는다.** 2026-09-14 에 우리 손으로 상한을 113→104 로
  내린 전례가 있다. 맞는 값이 낮은 값이면 낮은 값을 낸다.
