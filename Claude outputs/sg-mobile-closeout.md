## 2. 남은 하나 — **320px 의 `/` 하나. 내비가 아니다**

네 불확실 #1 이 320px 을 안 봤다고 했다. 봤다. 거기 하나 남아 있다.

    320px · `/` 만    scrollWidth 340 / viewport 320   → **20px**

원인을 조상까지 따라가 봤다. **내비가 아니다.**

    그리드 컨테이너   padding 24px / 24px
                     grid-template-columns → **316px** 로 풀린다
                     min-width 0 · max-width 1248px
    결과             24 + 316 = **340**  (320px 안에 안 들어간다)
    넘치는 요소       DIV.hero-say · H1 · P.lead
                     ⚠ 이 셋은 **자기 내용이 넘치는 것이 아니다** —
                       scrollWidth == width == 316 이다. 칸이 316 으로
                       고정돼 있어서 밀려나는 것이다

**히어로 그리드의 칸 하한 문제다. 글자 문제가 아니다.**
(`모바일_320_랜딩_잔여넘침.png`)

### 판정 — 본선. 오늘 안 고친다

    ① 범위가 작다      20px · **`/` 한 화면** · **320px 한 폭.**
                      360 이상 전부 깨끗하다. 320px 은 1·2세대 SE 와 구형
                      안드로이드다 — 현행 SE 는 375 다
    ② 크기가 다르다     내비는 미디어쿼리 한 규칙이었고 전/후를 재서 끝났다.
                      이건 **그리드 칸의 하한**이라 히어로 레이아웃을 건드리고,
                      모든 폭을 다시 재야 한다
    ③ 배포 예산        오늘 세 번 배포했다. 투표 이틀 전에 네 번째를 320px
                      20px 에 쓰는 것은 얻는 것보다 위험이 크다
    ④ 그리고 `/` 는     제출 이미지 여섯 중 하나다. 히어로를 건드리면
                      다시 떠야 할 수 있다 (내비 수정은 16:9 라 그럴 필요가
                      없었다 — 이건 다르다)

미완에 적어라. 위 실측값(24 + 316 = 340 · `grid-template-columns` 가 316 으로
풀린다)을 **그대로** 넣어라. 다음 세션이 다시 찾지 않게.

## 3. ⚠ 네가 찾은 순서 문제 — **내 처방의 결함이고, 내 시험이 그걸 숨겼다**

너는 내 (A) 를 그대로 넣었더니 108px 이 나왔고, 원인이 **선언 순서**였다고
보고했다 — `nav.pages` 가 374행·541행 두 벌이고 미디어쿼리가 그보다 앞이라
같은 명시도에서 뒤엣것의 `gap:28px` 가 이겼다.

**맞다. 그리고 내가 그걸 못 본 이유가 내 시험 방법이다.**

나는 `page.add_style_tag()` 로 CSS 를 **주입**해서 (A) 를 쟀다. 주입된 스타일은
캐스케이드의 **맨 뒤**에 붙는다. 그래서 순서 충돌이 애초에 일어날 수 없었고
`342×90` 이 바로 나왔다. **파일을 고치는 것과 주입하는 것은 다르다** —
내가 "검증했다" 고 말한 342×90 은 파일 안에서는 보장되지 않는 값이었다.

네가 실제 파일에서 부딪히고 **원인까지 짚어** 고친 것이 맞다. 그리고 그 이유를
CSS 주석과 검사 양쪽에 적은 것 — 순서가 잠긴다. 그게 §6 이다.

⚠ 나도 같은 것을 적어 둔다: **주입으로 잰 CSS 값은 처방의 근거로 약하다.**
  다음에 내가 CSS 를 검증하면 파일을 고쳐서 재겠다.

근거가 덜 재진 것이었다.

## 5. 네 불확실 둘에 대한 답

### #2 검사가 CSS 규칙만 본다 — **맞다. 그리고 그 약함을 적은 것이 옳다**

"접히게 돼 있다" 까지만 말하고 "안 넘친다" 는 못 말한다고 docstring 에 적은 것 —
그게 정확하다. 약한 검사를 강한 것처럼 적지 않았다.

**실제 폭을 재는 검사는 본선이고, 위 §1 의 표가 그 명세다.**
`scripts/` 아래 별도 스크립트로, 폭 목록 × 화면 목록 × `scrollWidth <= viewport`.
640/641 경계를 목록에 넣어라 — 미디어쿼리가 꺼지는 자리가 제일 잘 깨진다.

### #3 `nav.pages` 가 두 벌 — **합치는 것이 옳고, 오늘 범위 밖인 것도 옳다**

두 벌이 있는 채로 순서에 의존하는 구조다. 지금은 주석과 검사가 그 순서를
잠그고 있으니 조용히 깨지지는 않는다. 합치는 것은 본선.

### `⚠` 가 이모지 가드에 걸린 것

반복되는 자리라고 적은 것이 중요하다. 미완에 한 줄 남겨라 — **주석의 `⚠` 는
`주의(중요)` 로 쓴다**가 이 저장소의 관례다. 가드를 고치는 쪽이 아니라 관례를
적는 쪽이다(가드를 느슨하게 하면 화면 문구에서 새어 나간다).
