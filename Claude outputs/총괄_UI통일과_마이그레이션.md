히어로는 `.lv2-hero`/`.intro`, 바닥글은 `footer` 를 지목**해 쟀습니다.

# 1부. UI 통일 — **예상보다 훨씬 통일돼 있습니다**

## 통일된 것

    헤더        `masthead` **65px · 내비 5개** — 8장 전부 같음
    바닥글      `site-foot` **145px** — 8장 전부 같음
    히어로 제목  **60px** — 8장 전부 (어제 네 장이 34px 이던 것이 고쳐짐)
    히어로 패딩  `.intro` 7장 전부 **32px/24px**
    아트·eyebrow 8장 전부 있음

## 갈리는 것 넷 — **셋은 설계, 하나는 결함입니다**

### ⚠⚠ 결함 — `/scan` · `/batch` · `/watch` 에 **`<h1>` 이 없습니다**

    화면        h1  h2  h3
    /            1   5   0
    **/scan      0   1   3**   ⚠
    **/batch     0   1   2**   ⚠
    **/watch     0   1   0**   ⚠
    /guide       1   1   0
    /samples     1  10   0
    /misses      1   3  12
    /unknown     1   9   0

**세 화면이 `<h2>` 로 시작합니다. 그 위에 `h1` 이 없습니다.**
그리고 **`/scan` 이 우리 메인 도구 화면입니다.**

    접근성    스크린리더가 페이지 주제를 잡지 못합니다
    SEO      검색엔진이 페이지 주제를 약하게 읽습니다
    구조     h1 없이 h2 로 시작하는 문서입니다

⚠ **어제 레이아웃 에이전트가 이 자리를 보고도 지나갔습니다.** 히어로 눈금을
  고칠 때 *"태그를 맞추는 대신(**그 태그가 문서 구조상 맞습니다**)"* 이라고
  적고 CSS 로만 풀었습니다. **그 근거가 틀렸습니다** — `h1` 이 아예 없는
  페이지에서 `h2` 가 첫 제목인 것은 문서 구조상 맞지 않습니다.

⚠⚠ **그리고 저도 못 잡았습니다.** 어제 "히어로 8/8 60px" 만 재고 통과시켰고,
  **크기만 보고 구조를 안 봤습니다.** 오늘 §6 에 넣은 그 규칙을 또 밟았습니다 —
  무엇을 셀 것인지 정할 때 "크기" 만 넣고 "태그" 를 안 넣었습니다.

**고치는 법**: `/scan`·`/batch`·`/watch` 의 히어로 제목을 `h2` → `h1` 로.
CSS 는 이미 둘 다 받으므로 **마크업 세 줄**입니다.
⚠ 검사에 "모든 화면에 `h1` 이 정확히 하나" 를 넣으십시오 — **본 화면 수를
  같이 단정**해서.

### 설계 ① 배지 — `/batch`·`/guide` 에 없음 · **고치지 마십시오**

그 두 화면은 **리콜을 대조하지 않습니다.** 배지를 달면 대조한 것처럼
읽힙니다. 기존 검사가 그 규칙을 강제합니다.

### 설계 ② 히어로 컴포넌트 — `/` 만 `.lv2-hero`(789px), 나머지 `.intro`(281~302px)

랜딩은 마케팅 화면이고 나머지는 도구 화면입니다. **다른 것이 맞습니다.**
⚠ 다만 `.intro` 7장의 높이 차(281·294·302)는 **내용 길이 차이**이지 규칙
  차이가 아닙니다 — 패딩이 전부 같습니다.

### 설계 ③ `<main>` 클래스 — 5장 없음 / 3장 `.container gd|sx|mx`

레이아웃 에이전트가 *"억지로 맞추면 랜딩 띠가 깨진다"* 고 멈추고 **좌측선이
여덟 장 모두 96px 인 것**을 쟀습니다. **보이는 것은 어긋나지 않습니다.**

# 2부. React / Next 마이그레이션 — **가능합니다. 다만 지금은 아닙니다**

## 규모 (실측)

    화면 HTML        8장 · **3,019줄**
    인라인 JS        약 **1,992줄**
    외부 JS          380줄
    CSS             1,445줄
    ────────────────────────────
    HTML·CSS 를 읽는 **검사 파일 71개**

## 가능한가 — **네**

3천 줄은 작습니다. 화면 8장, 상태도 단순합니다(폼 → 제출 → 결과 표시).
**기술적으로 막는 것은 없습니다.**

그리고 **이미 절반쯤 와 있습니다** — 어제 만든 `layout.py` 가 머리글·바닥글·
내비를 서버에서 박습니다. **서버 컴포넌트의 역할을 이미 하고 있습니다.**

## 드는 것

    화면 8장 컴포넌트화              2~3일
    인라인 JS 1,992줄 → 상태로 옮기기  3~5일   ← 가장 큽니다
    **검사 71개 파일 재작성**          ?      ← **여기가 진짜 비용입니다**
    배포 구조 재설계                  1~2일

## ⚠⚠ 진짜로 걸리는 것 — 검사가 아니라 **검사가 지키는 것**

이 저장소의 가드는 **마크업을 문자열로 읽습니다**:

    srccheck.markup_only        주석을 뺀 마크업만 본다
    이모지 가드 · 단정 표현 가드   §9 금지어를 화면에서 잠근다
    문구 완전성 검사             화면의 모든 줄이 서버에서 오는지
    test_design_tokens          폰트·색·모서리
    test_frontend PAGES         화면 목록

**React 로 가면 이것들을 「렌더해서」 봐야 합니다.** 검사가 무거워지고,
§6 의 *"틀이 아니라 틀에 붓는 값을 본다"* 가 훨씬 어려워집니다.

⚠ **그 검사들이 오늘 하루만 해도 이만큼 잡았습니다**: 「잠시 후」가 축 카드에
  남은 것 · `(주)` 표기가 화면으로 나가는지 · §9 고지문이 여덟 장에 있는지 ·
  Pretendard GOV 가 코드에 들어왔는지 · 깨끗한 환경에서만 깨지는 머리글.

**이 제품이 지키려는 것(R1~R7·§9)을 지키는 것이 그 검사들입니다.
스택을 바꾸면 지키는 장치부터 다시 만들어야 합니다.**

## 그리고 배포가 늘어납니다

    지금    FastAPI 한 개 · fly 한 앱 · 볼륨 하나
    Next    프런트 앱 + API(FastAPI 유지) = **배포 대상 둘**

⚠ **어제 겪은 것을 생각하십시오** — 국표원이 도쿄에서 안 닿아 경유지를
  세웠습니다. **배포 대상이 늘면 그런 문제도 늡니다.** 지금 앱 하나에
  경유지 하나인데, 넷이 되면 어제 같은 밤이 또 옵니다.

## 언제 하면 되는가 — **조건 셋**

    ① 화면이 **15장 이상**이 될 때      지금 8장. 컴포넌트화 이득이 작습니다
    ② 화면에 **상태**가 늘 때           지금은 폼→결과. 상태 관리가 필요 없습니다
    ③ 검사를 **렌더 기반으로 옮길 여력**  이게 전제입니다. 먼저 옮기고 나서 이사합니다

**셋 중 하나도 지금 충족되지 않습니다.**

## 중간 길 — **이게 답입니다**

`layout.py` 가 이미 머리글·바닥글·내비를 한 곳에서 박습니다. **더 잘게
쪼개면 컴포넌트화의 이득을 대부분 얻습니다** — React 없이, 검사를 그대로
두고.

    layout.py 가 지금 박는 것   머리글 · 바닥글 · 내비 · 건너뛰기 · §9 고지문
    더 옮길 수 있는 것          히어로 블록 (`.intro` 7장이 같은 모양입니다)
                              카드 · 칩 · 축 같은 반복 조각

⚠ **오늘 히어로 h1/h2 가 갈린 것도, 히어로가 8벌로 복붙돼 있어서입니다.**
  `layout.py` 가 히어로도 박으면 그 갈림이 구조적으로 불가능해집니다.
  **React 로 가서 얻으려던 것이 정확히 그것입니다.**
