### `7a6fd70` SCoC 오탐 제거 — **원칙이 하나 생겼다**

전안법은 위해도 4단계고 가장 낮은 **공급자적합성확인(SCoC)** 은 제조·수입자가
스스로 시험해 확인한다. 그래서 **정부 조회 DB 에 인증번호가 없는 것이 정상**이다.
설계서 p.10 예시에서 리콜 레코드의 `certNum` 에 "공급자적합성" 문자열이 오는 것도
같은 맥락이다.

그런데 코드는 미조회를 무조건 RED 로 봤다. **부재를 위반으로 읽은 것**이고 R3 와
정면 충돌한다. 오탐 RED 가 반복되면 셀러가 모든 RED 를 무시하게 되고, 그러면 진짜
취소된 인증도 안 보게 되어 애초에 고치려던 문제로 돌아간다.

**CLAUDE.md R3-b 로 명문화:**

> RED 는 정부 DB 가 문제를 적어둔 경우에만. 부재는 증거가 아니다.

| 신호 | 조건 |
|---|---|
| **RED** | 취소·효력상실·표시 사용금지, 리콜 목록 일치 — 전부 DB 가 적극적으로 말해준 것 |
| **AMBER** | 미조회, 인증번호 없음, 유해물질 기준 적용, 처분 조치 진행 |
| **UNKNOWN** | 판단 근거 부족 |
| **GREEN** | 인증·리콜 두 축의 적극적 증거 |

부수 변경: `is_cert_number()` 로 "공급자적합성" 같은 자리표시자를 인증번호와 구분.
안 걸러내면 같은 자리표시자를 가진 서로 다른 상품이 전부 일치로 잡힌다.

## 5. 현재 신호등 동작 (프로덕션에서 확인)

```
미조회(SCoC 가능)  → kc_not_found / AMBER    ← RED 에서 빠짐
취소된 인증        → kc_revoked   / RED      ← 유지
표시 사용금지      → kc_suspended / RED      ← 유지
리콜 일치          → recall_match / RED
```

⚠ 미조회의 **최종 신호는 UNKNOWN 으로 나온다.** `coverage_gap`(규칙 DB 전부 draft)이
먼저 걸려 UNKNOWN 으로 떨어지기 때문이다. finding 자체는 AMBER 를 달고 있다.

R3 가 의도한 우선순위라 정상이고, **규칙 DB 가 승격되면 AMBER 로 드러난다.**
즉 검수가 끝나야 신호등 세 단계가 다 보인다.

## 8. 이 세션에서 배운 것 (반복 방지)

**패치·파일은 반드시 디스크로 받는다.** 대화 텍스트로 옮기면 깨진다. 이번에 두 번
겪었다 — 처음엔 UTF-8 이 Latin-1 로 읽히는 모지바케, 다음엔 base64 를 옮기다
문자열이 끼어들었다. **sha256 대조로 둘 다 걸러냈다.**

**깨진 값을 추측으로 복원하지 않는다.** `cert_states` 문자열이 한 글자만 달라도
`classify_cert_state()` 가 조용히 UNKNOWN 으로 떨어지고, 취소된 인증이 RED 가
아니게 된다. 고치려던 버그가 다른 형태로 남는다.

**작업 시작 전에 최신본인지 확인한다.** 오래된 스냅샷으로 작업해 커밋 하나를
통째로 버렸다 (API 매핑을 두 번 만들었다).

**Bash heredoc 이 auto mode classifier 에 막힌다.** 파일 쓰기는 Write 도구를 쓴다.
