## 0-a. 세션 분담 — 같은 큐를 둘이 잡지 않는다

세션이 둘이라 같은 항목을 잡으면 rebase 가 반복되고, **한쪽 커밋이 다른 쪽
판단을 모른 채 얹힌다.** 규칙 셋 (2026-09-13 총괄):

    (1) 항목을 시작할 때 여기에 "잡음 — [항목] · 세션명" 한 줄을 **먼저 push**
    (2) 그 항목이 push 될 때까지 다른 세션은 **같은 파일군을 건드리지 않는다**
    (3) 시작 전 `git pull --rebase`

    A (Bumpist)   [I 정정] → [제출-2] 화면(B·C·D) + 디자인 적용
                  파일군: static · docs/I_… · 미완 1-c · design/
    B (sooknise)  [L-1] → [L-2] → [M-5]
                  파일군: 새 yaml · models.py 표 · verifier 안내 문장

⚠ **`models.py` 를 건드리는 것은 B 뿐이다.**

## 1. [제출-1] 제출문을 기준선 하나에 묶었다

### 1.1 ⚠⚠ 찾은 것 — 제출문이 **자기가 선언한 원칙을 다음 문장에서 어겼다**

제출문 §2 1000자판:

    단건: "사람이 검수한 쌍만 세면 **95건(70.4%)**, 검수하지 않은 18건을 모두
           정답으로 가정한 상한은 **113건(83.7%)**. **두 값을 함께 적는 이유는
           검수 전 숫자를 검수된 숫자처럼 쓰지 않기 위해서입니다.**"
    배치: "대량 검사 경로는 **82.2%** 입니다."          ← 한 값뿐

**82.2% 는 상한이다.** 검수 분리로 다시 재니:

    배치 · 상품명만 · 분모 135
      ① 검수된 정답  96 (71.1%)      ② 미검수 15
      ③ 상한        111 (82.2%)      ④ 0 · ⑤ 2

원칙을 선언한 바로 다음 문장이 그 원칙을 어기고 있었다. **심사 서류다.**

왜 안 잡혔나: 숫자가 두 곳에 따로 있었다 - `test_item_grades` 에 하드코딩된
`ok == 111` 과 제출문의 "82.2%". 둘을 잇는 것이 없었다 (§6).

### 1.2 고친 것

`scripts/audit_tally.BASELINE_BATCH` 를 만들어 **한 곳**으로 모으고
`batch_tally()` 로 재생한다. 단건 재생과 **같은 `tally`** 를 쓴다 - 집계를 다시
적으면 두 경로가 갈린다(2026-09-08 에 구현이 셋이라 77.8% 를 적었던 일).

제출문 §2 를 고쳤다:

    후: "데모와 같은 단건 경로 기준이고, 대량 검사 경로도 같은 방식으로
         **96건(71.1%) · 상한 111건(82.2%)** 입니다."

## 6. [IP 스크럽] 공개 리포였다 — 옛 커밋 넷에서 지웠다

### 6.1 ⚠⚠ 내가 전제를 확인하지 않았다

`e0cf1df`(옛 `bead877`)에서 "공인 IP 는 ISP 가 바꾸고 포트가 열려 있지 않으면
노출 가치가 낮아 **지우는 비용이 남기는 위험보다 크다**" 고 적었다.

**그 판단은 리포가 비공개라는 가정 위에 있었고, 가정을 확인하지 않았다.**

    curl -s -o /dev/null -w "%{http_code}" https://api.github.com/repos/parksubeom/sourcing-guard
      → **200**   (인증 없이 · 비공개면 404)

공개다. 총괄이 준 조건("공개거나 공개 예정이면 지금 지우는 게 맞다")에 해당한다.

⚠ 값이 맞아도 전제가 틀리면 결론이 틀린다. **확인할 수 있는 전제는 확인한다** -
  "총괄의 말도 검증 대상이다"(09-08)의 자기 판단 판이다.

### 6.2 무엇이 어디에 있었나

IP 는 **커밋 메시지가 아니라 파일 내용**(`docs/작업로그_2026-09-13.md` 한 줄)에
있었다. 트리에 든 커밋은 `3bfdb64` · `f07238e` 둘이고 `bead877` 이 지웠다.

### 6.3 한 것 (§6 절차 · 총괄 확인함)

    1. 백업       로컬 태그 + 로컬 브랜치 `backup/pre-ip-scrub-2026-09-13`
                  → 옛 HEAD `80fcfbebe9859ba6bd52176704fe9951ae2f6466`
    2. 스크럽     `git filter-branch --tree-filter` 로 `3bfdb64~1..HEAD` 의
                  해당 파일에서 IP 문자열만 치환
    3. 확인       최근 커밋에서 IP 0건 · **최종 트리 동일** `e34a06ca…`
    4. push       `--force-with-lease` · `80fcfbe → 37ef4a7`

⚠⚠ **최종 트리가 스크럽 전과 같다.** 지금 파일 내용은 한 글자도 안 바뀌었다 -
  바뀐 것은 중간 커밋 둘의 트리와 그 뒤 커밋들의 해시뿐이다.

### 6.4 ⚠ 스크럽 중에 내가 한 실수 하나

**백업 태그를 원격에 push 했다.** 2026-09-09 rewrite 의 전례를 따랐는데,
그때는 목적이 **해시 참조 보존**이었고 이번은 **값 제거**다. 원격에 백업이
있으면 공개 리포에서 옛 커밋이 그대로 닿아 **스크럽의 목적이 무너진다.**

    올린 것을 5분 뒤 지웠다 (`git push origin :refs/tags/...`)
    되돌릴 근거는 **로컬에 태그 + 브랜치 이중**으로 붙들어 뒀다

⚠ 같은 이름의 백업이라도 **목적이 다르면 두는 자리가 다르다.**
  `backup/pre-rewrite-2026-09-09` 는 원격 영구 보존(§6 · 지우지 말 것),
  `backup/pre-ip-scrub-2026-09-13` 은 **로컬 전용**이다.

⚠ GitHub 는 force push 뒤에도 참조 없는 객체를 한동안 보관한다. 일반 조회로는
  안 보이지만 **완전 제거는 GitHub 지원 요청이 필요하다.** 값의 민감도를 보면
  거기까지 갈 일은 아니라고 보지만, 총괄이 다르게 보면 말해 줄 것.

  눈이 놓친 둘을 잡았고, 이번엔 반대다. 한쪽만 하면 절반을 놓친다.

### 7.2 [C-화면] — `alerts[]` 는 생겼다. 문제는 화면이 그것을 말하는 방식이었다

RED 데모 상품(모형완구 기차놀이 · CB067R317-5002)을 `/watch` 에 등록하고

    strength      exact
    matched_on    kc_number
    공표일         2026-07-23
    사유           프탈레이트계 가소제 기준치 49.5배 초과 (DINP 4.843 %)

그런데 화면이 넷을 잘못 말했다. 셋은 셀러에게 거짓말이다.

| | 증상 | 원인 | 어느 방향인가 |
|---|---|---|---|
| ① | 알림 1건이 **두 줄**로 | 버튼 핸들러와 `load()` 가 `freshAlerts` 를 둘 다 채운다. 스윕이 방금 저장한 알림이 양쪽에 있다 | **없는데 있다고** |
| ② | 저장된 알림 0건인 소유자에게 "새 알림 1" | `last_full_sweep_new` 는 **전 소유자**를 돌고 적은 전역 값 | **남의 것을 내 것이라고** |
