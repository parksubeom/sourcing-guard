## 3. [①-b] performance 문장 되살리기

유해물질 분기를 세 갈래로 바로 세웠다. 전에는 `performance` 가지가 문장만
만들고 `continue` 를 안 해서 **아래 공통 블록이 그 문장을 버렸고**,
`requirement` 가지의 `continue` 뒤에 같은 append 가 한 벌 더 놓여 도달하지
못했다.

```
전 (실측)  이 품목에는 '승차용 안전모 안전요건' 기준이 적용됩니다.
           시험성적서로 확인이 필요합니다.
           detail={'rule_id': 'KC-LIFE-HELMET-PERF'}

후         이 품목은 안전확인 안전기준 부속서 52(승차용 안전모) 대상입니다.
           충격 흡수, 유지 시스템 강도, 내관통 시험을 통과해야 하며, 공급처에
           시험성적서를 요구하세요. 참고로 국가기술표준원 해외 구매대행
           안전성조사(2026-05-14)에서 이 품목은 10개 중 7개가 안전기준에
           부적합했습니다. 표적 조사이고 표본이 작아 일반화할 수는 없으나,
           확인 없이 소싱하기에는 위험이 큽니다.
           detail={... test_items: ['충격 흡수','유지 시스템 강도','내관통'],
                    failure_rate: {sample: '10개 중 7개', source: ...}}

           휴대용 레이저용품도 같다 - 겉모양·구조·레이저의 등급 · 10개 중 8개.
```

**왜 아무도 못 봤나.** `tests/test_performance_rules.py` 가
`_performance_statement` 를 **직접 불러서** 재고 있었다. 단위 검사는 통과하는데
화면은 다른 문장을 받는 자리다 — 부르는 쪽을 지나가는 검사가 없으면 죽은 코드가
살아남는다. 이제 `verify()` 를 지나가는 검사 넷을 넣었다(목 모드 휴리스틱으로는
헬멧에 category 가 안 잡혀 룰이 안 걸리므로 `facts` 를 직접 만든다).

반대 방향으로 재 봤다:

```
performance 가지의 continue 를 지우면
  FAILED test_performance_statement_survives_to_the_finding[승차용 안전모…]
  FAILED test_performance_statement_survives_to_the_finding[휴대용 레이저용품…]
continue 뒤에 append 를 한 줄 넣으면
  AssertionError: 도달할 수 없는 줄: [1725]
```

```

## 4. [②-abc] 감시 해제 · 신고 멱등 · 조사 병기 없애기

### 4-a. DELETE /api/v1/watch/{id}

소유자가 맞을 때만 지운다. **없는 id 와 남의 id 를 구분하지 않는다** — 둘 다
404 다. 구분하면 "그 id 는 존재한다" 를 남에게 알려 주는 셈이다.

그 항목의 알림도 한 트랜잭션에서 같이 지운다. 남기면 `alerts_for_owner` 가
watch_items 와 조인하므로 화면에서는 사라지지만 행은 남아 `alert_count()` 와
`/healthz` 가 계속 센다.

화면은 항목마다 "감시 해제" 버튼이고, 되돌릴 수 없으므로 한 번 묻는다.
서버가 204 를 준 **뒤에** 목록을 다시 그린다 — 화면에서 먼저 지우면 실패했을 때
"사라진 줄 알았는데 있는" 상태가 된다.

### 4-b. report-miss 멱등

키는 (소유자 · 입력 텍스트 지문 · 정렬한 품목) 의 SHA-256 이다. 원문을 색인에
통째로 넣지 않는다(20만 자까지 온다). 품목은 정렬해서 넣는다 — 순서가 키를
가르면 같은 신고가 두 줄이 된다.

```
1회차  201  4912d6b53b4b  "신고가 접수되었습니다…"
2회차  200  4912d6b53b4b  "이미 접수된 신고입니다…"
miss_reports.total  5 → 6      (두 번 눌러 +1)
품목 다름 201 · 소유자 다름 201 · owner 없으면 멱등 처리 안 함 (201/201)
```

⚠ **배포본 DB 에는 `dedupe_key` 열이 없다.** 열 추가를 스키마보다 먼저 돌린다.
주석이 걱정한 것을 실제로 재 봤다:

```
CREATE UNIQUE INDEX … ON miss_reports(dedupe_key)  →  OperationalError: no such column
```

그 예외는 `__init__` 에서 **DB 손상으로 읽혀 격리**된다 — 워치 항목이 통째로
사라진다. 옛 스키마 DB 를 만들어 열어 보고 확인했다: 격리 None · 옛 신고 2건
그대로 · 열 추가됨 · 멱등 동작.

### 4-c. 조사를 병기하지 않는다

`watchlist.py` 의 `'{subject}' 과(와)` 를 `models.with_particle` 로 바꿨다.

⚠ **와/과 는 나머지 셋과 반대다.** 받침이 없으면 '와', 있으면 '과' — 이/가·
은/는·을/를 은 받침이 없을 때 두 번째 형태를 쓰는데 이것만 첫 번째다.
`subject_particle` 결과를 그대로 뒤집어 쓰면 전부 틀린다. 검사가 그 비대칭을
직접 잠근다.

리포 전체에서 "과(와)·이(가)·을(를)·은(는)" 류 0회다. 가드는 **AST 로 문자열만**
본다 — 주석까지 세면 가드를 설명하는 줄이 가드를 깬다(이 저장소에서 열두 번 넘게
난 모양이라 처음부터 가른다).

반대 방향으로 쟀다:

```
watchlist.py 를 되돌리면
  AssertionError: ["sourcing_guard/watchlist.py:459 '과(와)'"]
```

/watch 의 확인 문구는 목적어를 앞으로 빼서 조사를 아예 없앴다 —
"'…' 감시를 해제할까요?"

```

다섯 숫자  95/18/113/0/3 무변화 · 도매꾹239 168/239 무변화
